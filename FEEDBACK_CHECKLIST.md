## Round 9 · after v0.9.1 (addressed in v0.10.0) · researched, as demanded

You were right to call for research; it found that the Touch ID feature as shipped in v0.6.0 could never have run, & the fix is an architecture change, not a patch.

Research findings, w/ sources:
- Tauri gives remote-origin windows NO IPC by default (pack doctrine, SOURCES-verified). DAMp's UI is served from http://127.0.0.1:{port}, which IS a remote origin to Tauri, so window.__TAURI__ was never injected: the biometric branch silently fell to the passkey modal every time. Silent fallback masked a dead feature for four versions; owned below. The doctrine's rule is also do NOT grant remote pages IPC, so the fix removes the page from the privileged path entirely.
- Keychain items created via the /usr/bin/security CLI carry an ACL trusting the security tool, not DAMp, which is why reads prompt & the experience read as "not storing" (compounded by the Passwords app never showing generic items). Items DAMp writes itself via Security.framework are silent for DAMp thereafter.
- Exact crate surface verified on docs.rs (objc2-local-authentication 0.3.2): canEvaluatePolicy_error -> Result, evaluatePolicy_localizedReason_reply w/ a sendable block2 reply block, & EVERY class feature-gated (LAContext + block2 features now pinned explicitly, likewise NSString/NSError on objc2-foundation); security-framework's passwords set/get_generic_password create-or-update & read the login-keychain item, & ItemSearchOptions w/ load_attributes gives a presence probe that never prompts.

- [x] 1. Touch ID not working · New architecture: the page talks ONLY plain HTTP to the engine (zero Tauri APIs; withGlobalTauri off again; capability ledger updated). On unlock, the engine prints a DAMP-CTRL BIOUNLOCK line; the shell (which already reads engine stdout) runs LAContext DeviceOwnerAuthenticationWithBiometrics, reads the passkey from the Keychain natively, & answers over loopback w/ the local header; the engine verifies the passkey against the vault hash & only then issues the token. The passkey never enters the page. The shell announces itself (& whether biometrics + a stored entry exist) at startup, so browser-mode & non-Mac fall back instantly w/o hangs.
- [x] 2. Not storing the code · Storage moved shell-side too: enabling (from the unlock checkbox or Settings) verifies the passkey engine-side, then the shell writes the entry itself w/ Security.framework (create-or-update, service ai.nodemode.damp.vault, account damp). Bc DAMp now OWNS the item, later Touch ID unlocks read it silently, no Allow dialog, & it is visible in Keychain Access. Entries you created earlier via the CLI or manually keep working (same service/account); the first DAMp read of such a foreign-owned entry may show macOS's one-time Allow prompt, after which DAMp rewrites on next enable.

### Corrections logged during Round 9 work
